# Hybrid Energy Optimizer v0.2.1 — Interactive Historical Dashboard Design

Date: 2026-10-01
Status: Proposed for user review

## 1. Goal

Turn the v0.2 real-data historical backtesting capability into an interactive Streamlit decision-support workflow that a non-developer can use without editing YAML or running CLI commands.

The dashboard should let a user choose a historical DK1 period, define a hypothetical wind-farm size and BESS size, run the same core backtest logic used by the CLI, and inspect the resulting economic and operating behavior.

This release is intentionally a presentation and usability release. It does not yet add battery degradation, grid-connection limits, DC-OPF, hydrogen, or dual/shadow-price analysis.

## 2. User problem

v0.2 can retrieve Energinet historical data and run a DK1 wind + BESS backtest, but the workflow is currently CLI-first and uses the abstract `wind_share` input. This makes the model harder to interpret and harder to demonstrate to recruiters, collaborators, and potential industry users.

v0.2.1 should answer a more intuitive question:

> For a hypothetical wind farm of a chosen size in DK1, coupled with a user-defined battery, how would historical operation have looked over a selected period under the current perfect-information model assumptions?

## 3. Scope

### In scope

- Preserve the existing v0.1 single-day/sample dispatch workflow.
- Add a Historical DK1 Backtest workflow to Streamlit.
- Let the user select start and end dates.
- Let the user enter wind-farm rated capacity in MW.
- Let the user enter battery power and energy capacity.
- Let the user choose initial and terminal SOC.
- Let the user choose HiGHS or Gurobi.
- Reuse the v0.2 Energinet ingestion and backtesting core; the dashboard must not reimplement optimization logic.
- Produce summary KPIs, daily charts, and a daily-results table.
- Make the model limitations explicit in the UI.
- Add tests for dashboard-facing orchestration/helpers without requiring live Energinet network access in CI.

### Out of scope

- Battery degradation cost.
- Grid connection constraints.
- Market forecasting or rolling horizon control.
- Intraday/balancing/reserve markets.
- DC-OPF / LMP / congestion rent.
- Hydrogen/electrolyzer assets.
- Multi-scenario sizing matrix.
- Claims about a specific real wind farm.

## 4. Wind-farm scaling approach

The existing v0.2 `wind_share` input is convenient for engineering tests but not intuitive for users. The dashboard should expose `wind_capacity_mw` instead.

For v0.2.1, the implementation should derive a normalized DK1 wind-production shape from the same Energinet regional history already used by v0.2, then scale that shape to the selected hypothetical wind-farm rated capacity.

The UI and documentation must clearly state that this is a representative hypothetical DK1 profile derived from regional aggregate history, not SCADA data from a specific asset.

The scaling helper must be isolated from the Streamlit page so it can be tested and replaced later when a better installed-capacity or asset-specific profile source is introduced.

## 5. Dashboard information architecture

The Streamlit app should present two main workflows:

### A. Sample / Single-Day Dispatch

Retain the existing v0.1 interaction for the synthetic sample case. This remains useful for transparent model validation and quick demonstrations.

Inputs:
- Battery energy capacity (MWh)
- Charge power (MW)
- Discharge power (MW)
- Initial SOC (MWh)
- Terminal SOC (MWh)
- Solver

Outputs:
- Baseline revenue
- Optimized revenue
- Revenue uplift
- Equivalent full cycles
- Wind/price chart
- Dispatch chart
- SOC chart
- Dispatch table

### B. Historical DK1 Backtest

Inputs:
- Market area: DK1 only in v0.2.1
- Start date
- End date (exclusive)
- Wind-farm capacity (MW)
- Battery charge power (MW)
- Battery discharge power (MW)
- Battery energy capacity (MWh)
- Initial SOC (% or derived MWh)
- Terminal SOC (% or derived MWh)
- Solver

Outputs:
- Backtested days
- Total wind energy
- Sell-all baseline revenue
- Curtail-negative baseline revenue
- Optimized revenue
- Battery incremental value vs curtail-negative baseline
- Total uplift vs sell-all baseline
- Equivalent full cycles

Charts:
1. Historical wind energy and electricity price
2. Daily battery incremental value
3. Daily revenue comparison: sell-all vs curtail-negative vs optimized
4. Daily equivalent full cycles

Table:
- Daily backtest results using the existing v0.2 result schema

## 6. Architecture

The dashboard must remain a presentation layer only.

Proposed structure:

```text
dashboard/
├── app.py
├── pages/
│   ├── sample_dispatch.py
│   └── historical_backtest.py
└── components/
    ├── charts.py
    └── metrics.py

src/energy_hub/
├── data/
├── backtesting/
├── optimization/
└── ...
```

The exact Streamlit page mechanism may be implemented either as tabs inside one app or as internal page modules, but business logic must stay under `src/energy_hub/`.

A small orchestration/service helper may be added under `src/energy_hub/backtesting/` if needed to convert dashboard inputs into the existing backtest request and return a structured result.

## 7. Data flow

```text
User inputs
    ↓
Dashboard validation
    ↓
Wind-capacity scaling helper
    ↓
Energinet historical client
    ↓
Validated hourly DK1 price + wind profile
    ↓
Existing daily backtest runner
    ↓
Existing wind + BESS optimizer
    ↓
Daily results + aggregate summary
    ↓
Dashboard metrics/charts/table
```

The CLI and dashboard must call the same underlying data/backtest functions so the project has one source of truth.

## 8. Error handling

The dashboard should surface clear user-facing errors for:

- end date not after start date,
- missing/late Energinet settlement data,
- incomplete 15-minute price groups,
- invalid battery parameters,
- invalid SOC values,
- solver unavailable,
- empty historical period after UTC trimming.

Errors from the core layer should be caught and displayed through `st.error(...)` without exposing a raw traceback in normal use.

## 9. Testing strategy

CI must remain independent from the live Energinet API.

Tests should cover:

- wind-capacity scaling behavior,
- dashboard input-to-config conversion,
- valid/invalid date handling,
- SOC conversion/validation,
- historical backtest orchestration with a fake Energinet client,
- summary KPI generation,
- chart-helper input expectations where practical,
- continued isolation of business logic from Streamlit.

Existing v0.1 and v0.2 tests must continue to pass.

GitHub Actions should continue to run installation, Ruff, pytest, and the existing sample optimization case.

## 10. UX and interpretation requirements

The Historical Backtest page must display a visible methodological note stating:

- the wind farm is hypothetical and derived from DK1 regional historical wind behavior,
- the historical optimization uses realized historical data and is therefore a perfect-information benchmark,
- results are model outputs, not realized asset PnL or investment advice,
- v0.2.1 does not yet include battery degradation or grid-connection limits.

The dashboard should prioritize interpretability over visual density.

## 11. Git workflow

1. Merge PR #2 (`feature/v0.2-real-data`) into protected `main` after required CI passes.
2. Create `feature/v0.2.1-historical-dashboard` from the updated `main`.
3. Implement with tests on that feature branch.
4. Open PR #3 to `main`.
5. Require GitHub Actions to pass before merge.

## 12. Acceptance criteria

v0.2.1 is complete when:

- a user can launch Streamlit and run the historical DK1 workflow without using the CLI,
- the user can choose dates, wind-farm capacity, battery power/energy, SOC assumptions, and solver,
- the result uses the same core backtest logic as the CLI,
- the dashboard displays the defined KPIs and four historical charts,
- the daily result table is visible,
- the model assumptions and limitations are visible,
- automated tests pass,
- GitHub Actions passes on the pull request,
- no live Energinet request is required by CI.

## 13. Follow-on work

The next release after v0.2.1 should focus on model credibility and storage economics rather than additional UI breadth:

- battery degradation / throughput cost,
- grid connection limit,
- hourly historical dispatch export,
- battery sizing sensitivity,
- dual/shadow prices,
- stored-energy value,
- eventually ED / DC-OPF and congestion analysis.
