# Hybrid Energy Optimizer v0.2.1 — Interactive Historical Dashboard Design

Date: 2026-10-01
Status: Implemented on `feature/v0.2.1-historical-dashboard`; final PR verification pending

## 1. Goal

Turn the v0.2 real-data historical backtesting capability into an interactive Streamlit decision-support workflow that a non-developer can use without editing YAML or running CLI commands.

The dashboard should let a user choose a historical DK1 period, define a hypothetical onshore wind-farm size and BESS size, run the same core backtest logic used by the CLI, and inspect the resulting economic and operating behavior.

This release is intentionally a presentation and usability release. It does not yet add battery degradation, grid-connection limits, DC-OPF, hydrogen, or dual/shadow-price analysis.

## 2. User problem

v0.2 can retrieve Energinet historical data and run a DK1 wind + BESS backtest, but the workflow is currently CLI-first and uses the abstract `wind_share` input. This makes the model harder to interpret and harder to demonstrate to recruiters, collaborators, and potential industry users.

v0.2.1 should answer a more intuitive question:

> For a hypothetical onshore wind farm of a chosen size in DK1, coupled with a user-defined battery, how would historical operation have looked over a selected period under the current perfect-information model assumptions?

## 3. Scope

### In scope

- Preserve the existing v0.1 single-day/sample dispatch workflow.
- Add a Historical DK1 Backtest workflow to Streamlit.
- Let the user select start and end dates.
- Let the user enter hypothetical onshore wind-farm rated capacity in MW.
- Let the user enter battery power and energy capacity.
- Let the user choose initial and terminal SOC.
- Let the user choose HiGHS or Gurobi.
- Reuse the v0.2 Energinet ingestion and backtesting core; the dashboard must not reimplement optimization logic.
- Add a tested DK1 onshore wind-capacity normalization layer based on Energinet installed-capacity data.
- Produce summary KPIs, daily charts, and a daily-results table.
- Make the model limitations explicit in the UI.
- Add tests for dashboard-facing orchestration/helpers without requiring live Energinet network access in CI.

### Out of scope

- Battery degradation cost.
- Grid connection constraints.
- Market forecasting or rolling horizon control.
- Intraday/balancing/reserve markets.
- DC-OPF / LMP / congestion rent.
- Hydrogen/electrolyzer assets.
- Multi-scenario sizing matrix.
- Claims about a specific real wind farm.
- Offshore farm-capacity normalization until an explicit offshore asset/price-area mapping is introduced.

## 4. Wind-farm scaling approach

The existing v0.2 `wind_share` input is convenient for engineering tests but not intuitive for users. The dashboard exposes `wind_capacity_mw` instead.

### 4.1 Reference data

Use Energinet Energi Data Service **DK1 onshore** settled wind production together with monthly `CapacityPerMunicipality` **onshore installed-capacity** data.

For each month represented in the requested historical period:

1. obtain the relevant monthly municipality-level onshore installed wind capacity,
2. aggregate only municipality codes explicitly mapped to West Denmark / DK1,
3. align that monthly onshore capacity with the hourly DK1 onshore wind-production series,
4. derive an hourly regional onshore wind-capacity-factor profile.

The DK1 municipality mapping lives in versioned, testable core code rather than Streamlit.

Offshore installed capacity is deliberately excluded from this MW-normalized pathway in v0.2.1 because the capacity dataset contains special/non-municipality location records that should not be silently forced into a DK1 municipality mapping. The legacy CLI `wind_share` pathway still uses aggregate settled onshore + offshore DK1 generation exactly as in v0.2.

### 4.2 Capacity-factor calculation

For hour `t` in month `m`:

```text
regional_onshore_cf[t]
  = DK1_onshore_wind_generation_mwh[t]
  / DK1_onshore_installed_capacity_mw[m]
```

For the 1-hour model resolution, MW average production and MWh per hour are numerically aligned. The implementation validates the resulting capacity factor and fails clearly on impossible or missing reference-capacity data rather than silently normalizing against an observed period maximum.

The selected hypothetical onshore wind farm is then:

```text
hypothetical_wind_mwh[t]
  = regional_onshore_cf[t] * wind_capacity_mw
```

This preserves the historical regional onshore production shape while giving the user an intuitive rated-capacity input.

### 4.3 Interpretation

The UI and documentation must clearly state that this is a representative hypothetical DK1 **onshore** profile derived from regional aggregate history and installed-capacity data, not SCADA data from a specific asset. Regional smoothing means it will generally be less volatile than an individual wind farm.

The scaling helper is isolated from the Streamlit page so it can later be replaced by asset-specific SCADA, reanalysis, power-curve modelling, or an explicit offshore mapping.

## 5. Dashboard information architecture

The Streamlit app presents two main workflows as tabs.

### A. Sample Dispatch

Retain the existing v0.1 interaction for the synthetic sample case. This remains useful for transparent model validation and quick demonstrations.

Inputs:
- Battery energy capacity (MWh)
- Charge power (MW)
- Discharge power (MW)
- Initial SOC (MWh)
- Terminal SOC (MWh)
- Solver

Outputs:
- Baseline revenue
- Optimized revenue
- Revenue uplift
- Equivalent full cycles
- Wind/price chart
- Dispatch chart
- SOC chart
- Dispatch table

### B. Historical DK1 Backtest

Inputs:
- Market area: DK1 only in v0.2.1
- Start date
- End date (exclusive)
- Hypothetical onshore wind-farm capacity (MW)
- Battery charge power (MW)
- Battery discharge power (MW)
- Battery energy capacity (MWh)
- Initial SOC (%)
- Terminal SOC (%)
- Solver

Outputs:
- Backtested days
- Total wind energy
- Sell-all baseline revenue
- Curtail-negative baseline revenue
- Optimized revenue
- Battery incremental value vs curtail-negative baseline
- Total uplift vs sell-all baseline
- Equivalent full cycles

Charts:
1. Historical hypothetical wind energy and electricity price
2. Daily battery incremental value
3. Daily revenue comparison: sell-all vs curtail-negative vs optimized
4. Daily equivalent full cycles

Table:
- Daily backtest results using the existing v0.2 result schema

## 6. Architecture

The dashboard remains a presentation layer only. The implemented structure is:

```text
dashboard/
├── app.py
├── sample_dispatch.py
└── historical_backtest.py

src/energy_hub/
├── data/
│   ├── energinet.py
│   └── wind_capacity.py
├── backtesting/
│   ├── runner.py
│   └── service.py
├── presentation/
│   └── charts.py
├── optimization/
└── ...
```

`dashboard/app.py` is a thin Streamlit router. User-input validation/orchestration lives in the reusable backtesting service, wind normalization lives under `src/energy_hub/data/`, and pure Plotly chart builders live in the installed `energy_hub.presentation` package so they can be imported and tested in a clean environment.

## 7. Data flow

```text
User inputs
    ↓
HistoricalBacktestRequest validation
    ↓
Energinet historical price + DK1 onshore wind production
    +
Energinet monthly municipality onshore installed wind capacity
    ↓
Explicit DK1 municipality aggregation
    ↓
DK1 regional onshore capacity-factor profile
    ↓
Scale to user-selected wind_capacity_mw
    ↓
Existing daily backtest runner
    ↓
Existing wind + BESS optimizer
    ↓
Daily results + aggregate summary
    ↓
Streamlit metrics/charts/table
```

The CLI and dashboard continue to converge on the same daily backtest runner and optimizer. The CLI keeps `wind_share` for backward compatibility in v0.2.1; the new capacity-based pathway is a reusable core API.

## 8. Error handling

The dashboard surfaces clear user-facing errors for:

- end date not after start date,
- missing/late Energinet settlement data,
- incomplete 15-minute price groups,
- missing monthly installed-capacity data,
- invalid or impossible regional capacity-factor calculations,
- invalid wind/BESS parameters,
- invalid SOC values,
- solver unavailable,
- empty historical period after UTC trimming.

Errors from the core layer are caught and displayed through Streamlit without exposing a raw traceback in normal use.

## 9. Testing strategy

CI remains independent from the live Energinet API.

Tests cover:

- monthly installed onshore wind-capacity parsing and DK1 aggregation,
- DK1 onshore capacity-factor calculation,
- wind-capacity scaling behavior,
- dashboard request-to-battery conversion,
- valid/invalid date handling,
- SOC conversion/validation,
- historical backtest orchestration with fake Energinet data clients,
- daily backtest and summary KPI behavior,
- pure chart-helper outputs,
- package/project version synchronization,
- continued isolation of optimization logic from Streamlit.

Existing v0.1 and v0.2 tests must continue to pass.

GitHub Actions installs the project, runs Ruff, Pytest, compiles `src` and `dashboard`, and runs the existing deterministic sample optimization case. CI does not call the live Energinet API.

## 10. UX and interpretation requirements

The Historical Backtest page displays a visible methodological note stating:

- the wind farm is hypothetical and derived from DK1 regional **onshore** historical production and installed-capacity data,
- it is a regional-profile approximation rather than an individual wind-farm SCADA trace,
- the historical optimization uses realized historical data and is therefore a perfect-information benchmark,
- results are model outputs, not realized asset PnL or investment advice,
- v0.2.1 does not yet include battery degradation economics or grid-connection limits.

The dashboard prioritizes interpretability over visual density.

## 11. Git workflow

1. Merge PR #2 (`feature/v0.2-real-data`) into protected `main` after required CI passes.
2. Create `feature/v0.2.1-historical-dashboard` from the updated `main`.
3. Implement with tests on that feature branch.
4. Open the implementation PR to `main`.
5. Require GitHub Actions to pass before merge.

## 12. Acceptance criteria

v0.2.1 is complete when:

- a user can launch Streamlit and run the historical DK1 workflow without using the CLI,
- the user can choose dates, hypothetical onshore wind-farm capacity, battery power/energy, SOC assumptions, and solver,
- regional DK1 onshore wind production is converted to a hypothetical rated-capacity profile using versioned installed-capacity reference data,
- the result uses the same core daily backtest/optimization logic as the CLI,
- the dashboard displays the defined KPIs and four historical charts,
- the daily result table is visible,
- the model assumptions and limitations are visible,
- automated tests pass,
- GitHub Actions passes on the pull request,
- no live Energinet request is required by CI.

## 13. Follow-on work

The next release after v0.2.1 should focus on model credibility and storage economics rather than additional UI breadth:

- battery degradation / throughput cost,
- grid connection limit,
- hourly historical dispatch export,
- battery sizing sensitivity,
- dual/shadow prices,
- stored-energy value,
- eventually ED / DC-OPF and congestion analysis.
